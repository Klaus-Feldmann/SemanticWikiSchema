# Selecting sources for a question

Choose methods to suit the task. Full-text search, category descriptions/members, structured SWS data and selected page documentation can be combined from the start. There is no mandatory source order and no requirement to inspect all schema fields before a simple full-text or category search. External research remains available when appropriate. Explicit user requests take priority.

Full-text search is a reasonable first candidate source when it indexes useful descriptions or documentation. Search the relevant namespaces explicitly where needed; the search tool's default content namespaces do not necessarily include templates, categories or users. Account for wording variants and the search provider's actual case/token behavior. A page title can be an identifier without describing its purpose.

For field-specific filters, discover the relevant schema and inspect the needed field labels, descriptions, types and select options. Use exact field keys and option IDs instead of inventing mappings or assuming FK1/FK2 have universal meanings. Concise application/use-case text can help select results if present. A field may be named Anwendung, Usage, Purpose or anything else: infer its role from the current definitions. No particular field, technical role flag or search checkbox is required. No such field is created automatically. Missing information does not disable the other search paths.

Use class, short description and application/use-case text as complementary selection evidence, without over-restricting to one class or one literal substring. Read the documentation for selected candidates when usage details are needed. Categories provide additional candidates and conceptual context, and are not relegated to a last-resort path.

sws-query-entities is a portable fallback for stored field filtering: it inspects one bounded page of schema members and their fields, not an indexed full-catalogue search. Its filters are AND-combined. equals compares primitive parts (select option IDs); contains is case-insensitive for textual parts. Follow nextCursor even when a page contains no matches. A complete negative would require inspecting every relevant page and establishing sufficient coverage/freshness. Derived/external data-view values are not included.

Graph capability information guides selection: known missing backends are not used, but unknown configuration does not block a requested read-only query. Actual endpoint responses establish success or failure, without treating transient errors as missing configuration. An unknown-configuration attempt carries a queryAdvisory text block.

Search indexes, category membership and graph projections can lag behind saves while runJobs executes. A successful query or exhausted pagination does not prove current or global coverage. Verify known candidate pages/entities directly where needed, and use sws-get-processing-status for per-page evidence. Do not resave pages, change schemas or trigger rebuilds merely because an index result is empty.

Own entity-level descriptions from the identity header are also selection evidence; they need not be schema attributes. SWS exposes them as localized descriptions metadata. Use indexed text to find candidates when supported, then read their descriptions through sws-get-subject or sws-get-page-subjects. The stored-field fallback only filters schema statements and does not pretend identity descriptions are statement keys.
